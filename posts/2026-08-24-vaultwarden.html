Vaultwarden: self-host your passwords without running Bitwarden's monster stack

August 24, 2026

Vaultwarden is an alternative server implementation of the Bitwarden Client API, written in Rust — and it works with the official Bitwarden apps and browser extensions you already use. The point isn't a different client; it's a server you can actually run at home. The official Bitwarden self-hosted image wants multiple gigabytes of RAM; Vaultwarden runs comfortably in tens of megabytes on a Raspberry Pi or the cheapest VPS you can rent.

At ~66k stars it's one of the most-starred self-hosted projects on GitHub, pushed as recently as today (August 24, 2026), with continuous development since early 2018. Formerly known as bitwarden_rs, if that name rings a bell.

One honest note from their own README: it's unofficial. The maintainers are clear it's not formally affiliated with Bitwarden Inc. — you're trusting the community build, which has an excellent track record, but know what you're signing up for.

Why you'd actually use it

  1. You want Bitwarden's polish without the subscription or the resource bill. Official clients sync to your server for free, including premium-ish features Vaultwarden enables (TOTP codes, file attachments, organizations) since it doesn't enforce Bitwarden's paid tiers.
  2. Family password sharing. Spin up an organization on your instance, share the streaming-passwords collection with family members using free Bitwarden accounts pointed at your server.
  3. Homelab single sign-on of life stuff. If you already run Traefik/nginx-proxy-manager and Authelia/Authentik, Vaultwarden slots into the standard "one more container behind SSO" pattern in minutes.
  4. Air-gapped / offline-first teams. Small teams that can't send secrets to any third-party cloud get full API compatibility on an internal network.
  5. Raspberry Pi / NAS duty. It's the canonical "runs great on ARM" workload — Synology and Unraid users have been deploying it via community containers for years.

Getting started

  1. Run the container (Docker method from the official wiki): 
    docker run -d --name vaultwarden \
  -v /vw-data/:/data/ \
  -p 80:80 \
  --restart unless-stopped \
  ghcr.io/dani-garcia/vaultwarden:latest
    Your encrypted vault database lives entirely in /vw-data/ — back that directory up and you've backed up everything.
  2. Or use Docker Compose: 
    # docker-compose.yml
services:
  vaultwarden:
    image: ghcr.io/dani-garcia/vaultwarden:latest
    container_name: vaultwarden
    restart: unless-stopped
    environment:
      DOMAIN: "https://vault.example.com"
      SIGNUPS_ALLOWED: "false"
    volumes:
      - ./vw-data:/data

  caddy:
    image: caddy:latest
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - ./caddy-data:/data
  3. Put TLS in front of it. This matters more than usual: the official Bitwarden clients require HTTPS (except plain HTTP on localhost). A minimal Caddyfile: 
    vault.example.com {
    reverse_proxy vaultwarden:80
}
  4. Open https://vault.example.com, create your account, then immediately flip SIGNUPS_ALLOWED=false (as above) so strangers can't register on your instance. Re-enable it temporarily whenever someone new needs an account.
  5. Point your devices at it: in every official Bitwarden app/extension, go to Settings → Server URL and enter your domain. Log in once; sync happens automatically after that.

Code & config samples

Most real configuration lives in environment variables or a config.json in the data dir. A hardened setup:

DATABASE_URL=/data/db.sqlite3        # or postgres://user:pass@host/vw for Postgres
DOMAIN=https://vault.example.com     # must match exactly, or CSRF checks fail
SIGNUPS_ALLOWED=false
INVITATIONS_ALLOWED=true             # invite family via email org invites
WEBSOCKET_ENABLED=true               # live sync across clients
ADMIN_TOKEN=$argon2id$...            # hash of your admin-panel password
EOF                                  # see wiki for generating the argon2 hash

Generate the admin token properly instead of pasting plaintext:

docker run --rm -it ghcr.io/dani-garcia/vaultwarden /vaultwarden hash

Nightly encrypted backup one-liner (SQLite path):

sqlite3 /vw-data/db.sqlite3 ".backup '/backups/db-$(date +%F).sqlite3'" \
  && gpg -c /backups/db-$(date +%F).sqlite3

Use the SQLite backup command rather than copying the file while it's being written, or you'll snapshot a corrupt mid-transaction state.

Troubleshooting

  • Clients can't log in over plain HTTP. Cause: official Bitwarden apps refuse non-TLS origins except localhost. Fix: terminate TLS with Caddy/nginx/Let's Encrypt in front of the container, and set DOMAIN to the exact public URL.
  • New logins return "Registration not allowed" or CORS errors. Cause: SIGNUPS_ALLOWED=false doing its job, or a DOMAIN mismatch between browser origin and configured value. Fix: match DOMAIN exactly (scheme included); temporarily enable signups when creating accounts.
  • Password reset emails never arrive. Cause: no SMTP configured, so the server can't send mail. Fix: set SMTP_HOST, SMTP_FROM, SMTP_USERNAME/SMTP_PASSWORD (and SMTP_PORT=587 with STARTTLS for most providers) before you need account recovery — this is the #1 regret among self-hosters who lock themselves out.
  • Mobile app doesn't live-sync changes. Cause: websocket support disabled or stripped by the reverse proxy. Fix: set WEBSOCKET_ENABLED=true and make sure your proxy forwards Upgrade headers; recent versions fold websockets into the main port, so also just update the image if you're on an old tag.
  • Admin panel won't accept your password. Cause: ADMIN_TOKEN was set as plaintext or the argon2 hash got mangled by shell escaping ($ characters). Fix: regenerate with the hash command shown above, and quote the value in compose files or use $${...} escaping.
